## 1. Problem and decision

Some callbacks are owned by a state visit, some by a spawned manager and some by an object lifetime. Current code mixes these boundaries. A host adds two local MainGameState handlers per visit; retained managers keep spawned subscriptions after despawn; an anonymous StressManager handler cannot be removed by a second lambda expression; three overrides bypass their identity's destruction fallback.

**Recommend OPTION 2: separate A, state/session subscriptions, from B, framework/network-object destruction cleanup.** Within A, use independent small commits rather than one manager-wide patch:

- **FIRST implementation slice A1: MainGameState callback ownership only.** One production file, one state-owned invariant, directly prevents duplicate local quit dispatch. No dependency requires changing StressManager or StationController alongside it.
- **A2: StressManager registration/delegate pairing.** Separate follow-up; the anonymous handler and early/full-spawn subscriptions share that owner.
- **A3: FloodManager and LevelManager spawned subscriptions and service registration.** Separate follow-up; preserve early station-registration order. Can be split by owner if verification proves independent.
- **B: StationController, ContractManager and TutorialWaitState framework destruction fallback.** Separate from A1, with narrow owner cleanup before required base destruction. Pool/rebind policy and feature registries require their own characterization rather than an automatic three-file rewrite.

Classes below mean **A = required in FIRST A1**, **B = real debt, separate task**, **C = already safe/obsolete claim**. These classifications are different from the two implementation tracks named A/B above.

## 4. Confirmed MainGameState failure and smallest correction

Installed StateMachine invokes `Enter(true)` when server, `Enter(false)` when client, then `Enter()` once (`StateMachine.cs:365–376, 548–555`). Host is both sides. MainGameState's lines 24–25 therefore append the same instance/method pair twice **before** its `if (!asServer) return`. `SettingsView.OnResume/OnQuit` (`UI/SettingsView.cs:53–66`) each invokes the corresponding static Action once; the Action invocation list contains the two entries.

Both handlers can actually execute twice. CloseSettingsView repeats HideView. QuitGame is async void: one multicast invocation can enter its body twice, call LeaveVoiceChannel twice and submit two lobby loads. Removing delegates during the first callback does not rewrite an already captured multicast invocation list. This is duplicate event dispatch, not proof of a separate async completion bug. RestartGame is added only in Enter(true), so it is **not** this host duplication.

Normal host Exit(true)/Exit(false) subtracts one matching local entry per call and leaves zero. Do not claim balanced state cycling grows the list. The smallest multiplicity correction is mutually exclusive side ownership: local settings handlers in the `!asServer` branch, server handlers in the server branch, with matching Exit branches. Parameterless Enter is an alternative but unnecessary; keep bool-side server progression unchanged.

For the full A1 lifetime invariant, **one local ownership flag is useful; one independent server-group flag is also needed**. These describe acquired registrations, not permission/authority or an async operation lock. They make duplicate Entry callbacks, overlapping Exit/Disable/despawn/destruction removals and current-state re-enable binding idempotent. Broad callback guards or a generic subscription framework are unnecessary.

## 7. Host/client and enabled lifetime behavior

Proposed Enter(false) binds the local pair and returns. Enter(true) acquires the server group while preserving the existing tutorial/normal branches and their publications. Matching Exit(bool) unbinds only that side. Client-only never owns restart/game-end/tutorial-finish handlers; server-only never owns resume/quit UI handlers. Host owns both distinct groups once.

OnDisable removes both owned groups; OnEnable rebinds only if `isSpawned && isCurrentState`, using live `isClient`/`isServer` to select groups. It must not emit startGame/startTutorial or run RestartGame/QuitGame. An inactive StateNode being enabled is not admission to this state. Enter on a disabled component may still be dispatched by the framework: skip binding while disabled, preserve existing server progression, and allow eligible re-enable to bind later. Normal network spawn is not a second state visit.

Side-specific OnDespawned(bool) unbinds that group's callbacks without relying on isServer/isClient having already changed; final parameterless OnDespawned removes any residue. Clear owned flags before removal. OnDestroy removes both groups, then calls base in finally. Shared helper removal must be safe before admission and after any combination of these boundaries. During machine teardown, Exit may already have removed the same group; repeat cleanup is harmless.

Already-running async handlers are separate lifetime work: removing a delegate prevents subsequent dispatch, not cancellation of a callback already selected/in flight. First-slice tests must distinguish that from a new post-teardown event invoking the old node.

## 8. Installed framework destruction semantics

Source truth: `NetworkBehaviour.cs` is an empty subclass of NetworkIdentity; `StateNode.cs` inherits it and has empty default Enter/Exit. `NetworkIdentity.cs:619–673` documents parameterless spawn/early-spawn/final-despawn once on host; bool variants run per side. Implementation at 1166–1335 invokes parameterless spawn on `_spawnedCount == 0`, early spawn once until reset, and final despawn after last side. Spawn flags are cleared **after** despawn callbacks. Never use an isSpawned check inside final removal to accidentally rebind.

`NetworkIdentity.OnDestroy:1117–1125`, except application quitting, calls TriggerDespawnEvent(false), TriggerDespawnEvent(true), then clears `_ticker`. TriggerDespawnEvent is side-spawn guarded, runs InternalOnDespawn, identity/external-module callbacks, decrements lifetime count and clears module collections on final exit. InternalOnDespawn at 492–514 removes registered tick/player/scene callbacks where applicable. SyncVar.OnDespawned (`NetworkModule/SyncVar.cs:163–175`) flushes as applicable and unsubscribes its tick manager; it does **not** clear arbitrary onChanged delegates. ### Proven/disproven scenarios and their limits

1. **Concrete source path in configured solo mode with two peers:** Host completes A (for example Quest1 movement); its server-ready body runs immediately and Next queues B. LateUpdate exits A, resets readiness and enters B (Quest2). Before the remote peer receives B, it completes its own A and sends progress then readiness. Both arrive at the server while B is current. The old count is written into B, and the old ready role sets B readiness. Solo CheckCompletion can queue C without completing B's tasks. Per-peer order is intact throughout; cross-direction latency permits this timing. This proves acceptance and mutation if that timing occurs, not that multiplayer testing observed a skip.
2. **Normal cooperative path is narrower:** with initialized role/view, one readiness per role, no independent replacement and ReliableOrdered delivery, A cannot normally advance before both A-ready commands have arrived; each sender's progress precedes its own ready. OnActionPerformed caps completed tasks and emits final readiness once per loaded visit. Latency alone does NOT establish a remaining A-ready message after cooperative advancement. Do not claim an unconditional normal cooperative race.
3. **Late application duplicate or state replacement:** an additional A-ready command arriving after B replaces A is accepted as B-ready. In cooperative mode it can prematurely satisfy B when the other B role is ready; a late A-progress command can misreport/regress B's partner count. This needs a duplicate/replacement stimulus; transport retransmission is not asserted to supply it. Exit cancellation protects unsent view work but cannot retract an RPC already serialized.
4. **Before LateUpdate:** repeated ready calls still invoke CheckCompletion even when SyncVar<bool> ignores an equal assignment. Two Next calls made while A remains current capture B twice; they do NOT capture B then C. B may be entered, exited and entered again, resetting its flags and presentation. In serialized solo mode, near-simultaneous legitimate completions from the two DIFFERENT roles can produce this without a same-role duplicate. Progress duplicates also forward notification despite unchanged SyncVar value. Base admission has no one-shot reservation; Quest6's existing terminal latch is preserved as an exception.
5. **Same-quest re-entry:** indices/state references identify content, not a visit. The installed SetState API permits replacement and re-entry; CanEnter/CanExit default true. Retain an A command while the same manager is replaced A -> B -> A: an index-only command is indistinguishable from a fresh A command at the new entry. This is a source/API counterexample to claiming index-only visit integrity, not a runtime-verified A -> B -> A scenario. Eliminating duplicate queued transitions does not prevent explicit same-state replacement.
6. **Shared task bridge:** WaitForPartner currently belongs only to Quest3 and WaitDoorOpen only to Quest5. A stale award after transition to a different current quest is normally rejected by action membership, so do not claim every delayed bridge message completes another quest. Same-quest re-entry, reused action definitions or duplicate awards for requiredAmount > 1 need originating context; current bridge arguments cannot provide it. Ordinary requiredAmount=1 repeats are capped locally.
7. **Teardown/re-entry:** TutorialManager has no application despawn/admission cleanup and retains its static reference; broader retained-manager debt stays OPEN. Framework send validation, identity routing/removal and RPC batch disposal provide session boundaries: no claim is made that a packet from a fully disconnected old session automatically reaches a new session. While the same manager is retained/valid, there is no application quest-entry admission to reject old intent. Session reuse must not rely on destruction or a local view counter.

### Problem, scope and chosen boundaries

Retained despawn left a live A in static Instance, so valid B.Awake destroyed B. The scoped design preserves the initial Awake claim, then reclaims a free slot in OnEarlySpawn(bool) on retained respawn. It never replaces a different live registered manager. An Awake-rejected duplicate is marked before deferred Destroy, preventing that pending-destruction object from later claiming a free slot. A previously valid retained A is not permanently rejected merely because B owns the slot during A's respawn; it can reclaim after B's lifetime ends.

Release uses ReferenceEquals(Instance, this), so old despawn/destruction cannot clear B. Bool despawn releases only if the opposite side is unspawned; final parameterless despawn also releases idempotently. This covers both full and early-only teardown. Destroy releases explicitly and preserves base.OnDestroy. Ordinary disable does not release network registration: disabled-but-spawned is distinct from despawn, and TutorialManager's existing disable admission invalidation remains unchanged. No serialized field, RPC, authority, readiness-entry counter or progression body changed; no asset/package migration is required. Rollback is limited to these ownership/lifetime additions, preserving the committed gameplay fixes.

TutorialInputManager's parameterless OnSpawned initializes only the exact accepted owner. Release cancels only that component's named LockInitialInteractions Invoke, including old-instance cleanup while B is current; B's invocation is unaffected. The existing 0.5-second startup timing, server radio reset and public callback bodies remain unchanged. **R7 remains OPEN / Medium, partially mitigated:** the despawn/replacement scheduled-writer path is cancelled; a still-valid lifetime's delayed startup lock racing a newer unlock/quest transition is not fixed or verified here. Do not treat this as complete startup-lock ownership or guard every stale RPC/public call by inference.

### Installed framework evidence and initialization compatibility

PurrNet package.json confirms 1.19.1. NetworkIdentity.SetIdentity assigns side flags before early spawn; HierarchyV2.RegisterIdentity/ManualEarlySpawn call TriggerEarlySpawnEvent before final spawn. TriggerSpawnEvent calls per-side OnSpawned(bool), then parameterless OnSpawned only when _spawnedCount is zero. StateMachine queues its initial SetState for LateUpdate. Awake remains the initial pre-network lookup boundary, and early reclaim occurs before queued state entry on retained respawn.

TriggerDespawnEvent calls the bool hook before clearing its side flag, and the parameterless hook when the full-side count reaches zero. ResetIdentity/pool reset explicitly triggers client/server despawn and clears identity state without rerunning Awake. NetworkIdentity.OnDestroy triggers both sides, except its quitting fast path; explicit manager release still runs before base.
